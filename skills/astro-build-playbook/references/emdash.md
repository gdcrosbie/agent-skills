# EmDash CMS for Astro

Read this when EmDash is the chosen CMS. The shared playbook still governs the approved design system, accessibility, assets and frontend verification; its static Content Layer and Static Assets hosting recipes do not configure this runtime.

## Architecture and API routing

Use a combined Astro frontend and EmDash CMS for a single site unless the project needs a separate consumer. Separate repositories are a choice, not a prerequisite. Keep approved layouts, styles and fonts, replacing their data access through a small frontend adapter. Do not use a CMS adoption task to redesign the site.

EmDash uses `output: 'server'`, a hosting adapter, the `emdash` integration, live collection registration and database/media storage. CMS content routes use live queries rather than `getStaticPaths`. The admin is at `/_emdash/admin`; Sveltia's `/admin/` shell and GitHub OAuth recipe do not apply.

For API details, load EmDash's supplied `building-emdash-site` skill if available in the project/session. Its references cover configuration, schema/seeds, queries/rendering and site features. Use `emdash-cli` for instance management and `creating-plugins` for plugin work when those skills are available. Do not hardcode a path into another project's checkout. If the supplied skills are absent, verify APIs against the installed package and official EmDash documentation; this reference is our integration methodology, not a replacement API manual.

Record installed Astro, EmDash, adapter and deployment-tool versions. The experience below was verified with EmDash 1.1.0–1.3.1, Astro 7.3.5–7.4.2, `@astrojs/cloudflare` 14.3.1 and Wrangler 4.146.0–4.147.0 (October 2026); recheck version-sensitive APIs and platform limits for a new build.

## Schema, import and presentation adapter

- Preserve entity boundaries and relationships. For a service catalogue, categories, services, locations and service/location prices are separate collections. Use reference fields with target collections and appropriate cardinality so editors can select records.
- Preserve source IDs for migration reconciliation where useful. Distinguish source IDs, CMS database identifiers and route slugs. In EmDash, `entry.id` is the slug used in URLs; `entry.data.id` is the database identifier used by APIs and joins.
- Map CMS field names explicitly. Custom snake_case fields remain snake_case; TypeScript casts do not rename them. On one build, the adapter's mistaken `availableAtAllLocations` access hid records whose actual field was `available_at_all_locations`.
- Check system/reserved field names before import. One build's price-formatting locale became `price_locale` because `locale` is EmDash's content locale column.
- Validate foreign keys, unique composite pairs, ordering and project coverage rules. For location prices, check amount, currency, availability and deliberate USD/CAD symbol disambiguation using the location's formatting locale. Test every imported pair, not just one illustrative price.
- Convert Markdown to Portable Text without losing headings, paragraphs or links; render rich text through the CMS renderer. Preserve source asset IDs and demo-data flags when needed for reconciliation and editorial clarity.
- Image fields are media objects, not URL strings. Render the object's source/alt or the supported EmDash image component; verify the resulting media URLs on the deployed host.
- Validate `seed/seed.json` with `validateSeed(seed)` from `emdash` before seeding. Every item in `menus[].items[]` requires an explicit `"type"` (`"custom"`, `"collection"`, `"entry"` or `"taxonomy"`); omitting it fails validation (`menus[0].items[i]: type is required`).
- Keep `emdash-env.d.ts` in sync with `seed/seed.json`. If `.wrangler/state/v3/d1` exists on disk with an unseeded SQLite database, `astro check` queries that empty database and overwrites `emdash-env.d.ts` with an empty `EmDashCollections {}`. Either seed or remove `.wrangler/state` before running `astro check` locally, or generate `emdash-env.d.ts` offline from `seed/seed.json` via `generateProjectEnvTypes(process.cwd())` (`emdash/dist/schema/project-env-types.mjs`).

Bundled images referenced by an external media object can support an explicitly scoped demo, but they do **not** create media-library records. State that limitation in the handoff. If editors need library management, import/upload the files through supported media APIs and attach real CMS media records. Preserve font licences when localising fonts.

Keep CMS failures visible. Do not quietly serve the seed as a fallback when live queries fail: that disguises missing content and lost edits.

## Query design and performance

Load only the data the route needs. A homepage needing two counts should not hydrate a catalogue's prices and relationships. Reuse collection results within a request; avoid reading every entry again merely to resolve references.

EmDash 1.1 collection reads do not automatically hydrate reference fields. Its per-entry reference API can create an N+1 query pattern when applied across a catalogue. Check whether the installed version offers a supported batch API before writing an optimisation.

A project-specific database adapter is an option when public APIs cannot efficiently serve the required graph. Make this judgement explicit and isolate the code. One build's adapter reads `_emdash_content_references` joined to `_emdash_relations` once, then matches `parent_group`/`child_group` against `translationGroup` on entries loaded through the published-content API. This is an **internal-schema dependency**, not a documented universal recipe:

- Use the request-scoped database. In EmDash 1.1, anonymous page middleware may expose a partial `Astro.locals.emdash` without `.db`; `getRequestContext()?.db` supplies the scoped connection. Do not assume the declared locals type guarantees a database property on every runtime path.
- Join against published entries so draft, deleted or unpublished targets remain absent. Preserve the required locale, preview, relation-field identity, cardinality and ordering semantics; collection-pair matching alone is insufficient if multiple relations connect the same collections.
- Record the internal tables and mapping used, and review the adapter on upgrades or schema changes. Verify required publication/preview behaviour rather than claiming parity with APIs that were bypassed.
- Register returned query cache hints when Astro caching is enabled. Do not add a cross-request catalogue cache without invalidation and preview semantics.

React is in the build because `@astrojs/react` powers EmDash's admin and its inline editor; visitors don't load it. In 1.4.0 the public toolbar for a signed-in editor is server-rendered, and React loads only when they switch **Edit mode** on (one `client:only` `InlinePortableTextEditor` island, about 1.35 MB compressed with its editor library) or open `/_emdash/admin`. When a performance check finds React in the network panel, confirm whether the browser was signed in before treating it as a visitor cost.

Measure live TTFB, page-render duration and database query count on representative routes before handoff. Inspect `Server-Timing` where available and compare before/after measurements from the same environment. Establish a project budget; do not turn one sample into a percentile benchmark or general service-level guarantee.

Observed results on one build: the original loader made 459 queries on a service response, and the homepage took 9.925 seconds to first byte. After batching and limiting homepage reads, live samples were 1.015 seconds / 10 queries for the homepage and 0.823 seconds / 13 queries for the service page. Query efficiency was the performance fix; a paid plan alone did not remove the delay.

## Cloudflare runtime and deployment

For Cloudflare, configure the Astro server adapter and EmDash D1/R2 adapters, plus the actual Worker bindings. Verify session and image-service bindings required by the installed adapter. Keep resource identifiers and credentials out of reusable recipes. Use the existing authenticated Wrangler workflow rather than extracting its OAuth token into another command.

Do not apply the static-only `assets.directory: './dist'` / no-`main` configuration to this server app. Let the selected Astro adapter produce its deployment configuration and inspect the resulting bindings. Settle one deployment path for the Worker and verify the deployed version.
- **Two-job GitHub Actions deploy (`--config dist/server/wrangler.json`):** During `astro build`, `@astrojs/cloudflare` writes the bundled Worker config to `dist/server/wrangler.json` (`"main": "entry.mjs"`, `"no_bundle": true`) and a redirect pointer to `.wrangler/deploy/config.json`. When a separate CI `deploy` job downloads only the `dist` artifact, `.wrangler/deploy/config.json` is absent, causing `wrangler deploy` to read the root `wrangler.jsonc` (`"main": "./src/worker.ts"`) and fail with `Could not resolve "virtual:astro-cloudflare:config"` / `"virtual:emdash/build"`. Always pass `--config dist/server/wrangler.json` to `wrangler deploy` in the `deploy` job.
- **Provision the `SESSION` KV namespace for Passkey auth:** EmDash stores the authenticated user ID in Astro's `session` (`session.set("user", { id: user.id })`). On Cloudflare Workers, `@astrojs/cloudflare` backs Astro sessions with a `SESSION` KV binding. Do **not** use `session: { driver: "memory" }` in production: in-memory sessions live only in a single Worker isolate, causing `/_emdash/admin` to repeatedly prompt for Passkey re-authentication whenever requests hit another isolate or after a deploy. Provision a KV namespace (`wrangler kv namespace create <name>-session`) and bind `{ "binding": "SESSION", "id": "<kv-id>" }` in `wrangler.jsonc`.
- **Scheduled publishing runs on the cron, never on a request.** EmDash's sweep promotes scheduled content from the Worker's `scheduled()` handler (`emdash/cloudflare`'s `createScheduledHandler()`), so the `triggers.crons` interval in `wrangler.jsonc` is the worst-case publishing delay: `* * * * *` (the starter's default) publishes within a minute, `*/15` up to 15 minutes late. **Publish now** / **Publish changes** write the live revision immediately and don't depend on the cron. The same handler runs cleanup and cache purges; with no page or object cache configured, those purges change nothing.
- **Global headers on SSR responses (`src/worker.ts`):** Under `output: "server"`, `public/_headers` only applies to static assets served from `env.ASSETS`. To enforce `X-Robots-Tag` (on private demos) and security headers on SSR HTML and API responses, wrap `emdash/cloudflare`'s default handler in `src/worker.ts` and set `"main": "./src/worker.ts"` in `wrangler.jsonc`. Use `X-Frame-Options: SAMEORIGIN` rather than `DENY` so `/_emdash/admin` preview and HTML-block iframes can render same-origin frames.
- **R2 media streaming and byte ranges (`HTTP 206`):** When serving large audio or video files (such as podcast MP3s) from the R2 binding (`env.MEDIA`), implement an Astro server route that parses RFC 9110 `Range: bytes=start-end`, calls `bucket.get(key, { range: { offset, length } })`, and returns `206 Partial Content` with `Content-Range`, `Accept-Ranges: bytes` and `Content-Length`. Podcast clients and mobile Safari `<audio>` scrubbing require `206 Partial Content`.
- **Resilient SSR rendering vs streaming truncation:** Astro streaming SSR flushes HTML chunks to the client immediately. If an SSR component or dynamic asset resolver throws an unhandled exception midway through rendering (for example, a missing image file or unhandled lookup error), Astro abruptly aborts the response stream. In the browser, this manifests as an elusive half-rendered page with a blank white box beneath the broken component while response headers still show HTTP 200. Always ensure dynamic asset and image resolvers implement safe fallbacks (returning a placeholder or logging a warning rather than throwing unhandled exceptions) so template execution never aborts the stream mid-response.

Plan and runtime limits are a distinct deployment concern. On one build, Worker logs confirmed `exceededCpu` at the then-applicable Free 10 ms CPU limit; the account owner enabled Workers Paid and the deployment accepted an explicit `limits.cpu_ms: 30000`. That is an observed project configuration, not a universal requirement or current pricing claim. Check current limits, expected usage and any paid requirements with the user before making a hosting choice. Do not upgrade their plan silently.

When a response is slow or fails, use response status, Worker logs and timing/query evidence to distinguish CPU exhaustion, database latency, inefficient queries and browser assets. A larger CPU allowance does not fix N+1 reads.

## Bootstrap, migrations and authentication

A seed bootstraps schema/demo content; editing its file is not an ongoing production migration. Preserve existing D1 content and user edits across deployments. When changing an established schema or importing content, use a deliberate supported migration/import workflow and verify the resulting records.

Inspect an existing database before assuming it is empty. Seeds may be applied in resumable batches; confirm completion and expected record counts before creating/handover of the admin account.
- **Cold-start schema auto-seed vs content seed (`includeContent: true`):** In EmDash 1.3.x, the cold-start auto-seed hook calls `applySeed(db, seed, { onConflict: "skip" })` with `includeContent: false` — creating collections, fields, menus and settings, but not `content` entries. To seed `seed.json` `content` entries before the owner registers their Passkey, send `POST /_emdash/api/setup` with `{"title":"...","tagline":"...","includeContent":true}`. Under built-in Passkey auth, this seeds all content entries and advances `emdash:setup_state` to `step: "site_complete"` while keeping `setupComplete: false`, so `/_emdash/admin/setup` prompts the owner directly to register their Passkey.
- **Post-setup D1 collection registration:** EmDash's setup auto-seed runs only when the database is empty (`emdash:setup_complete: false`). Once `emdash:setup_complete` is set, adding a new collection to `seed/seed.json` does **not** auto-create D1 schema tables or collection records on boot. Adding a new content type after initial setup requires an explicit D1 migration that registers the collection in `_emdash_collections`, defines field schemas in `_emdash_fields`, and creates the `ec_<slug>` content table. Furthermore, frontend CMS query functions in `src/lib/cms.ts` should provide an in-memory fallback array so the frontend never 500s or hangs during cold boots or database migrations.

- **Owner passkeys can be single-device.** A passkey registered in an embedded or automation browser (an agent's browser pane, a test profile) lives only in that browser's store and won't appear in Safari, another browser or a password manager. The `credentials` table shows it: `device_type = 'singleDevice'`, `backed_up = 0`, `transports = '["internal"]'`; a synced passkey (iCloud Keychain, 1Password, Bitwarden) reports `multiDevice` / `1`. There is no fallback sign-in unless an email provider plugin enables magic links. At handover, have the owner register in a browser backed by their password manager, or add a second admin with a synced passkey, and confirm the metadata with a read-only query (no key material): `select c.name, c.device_type, c.backed_up, c.transports, u.role from credentials c join users u on u.id = c.user_id`. Password-manager browser extensions can also intercept the WebAuthn prompt (Bitwarden's "Use your device or hardware key" passes it back to the browser).
- **Writing production content without the admin** (owner's instruction only; prefer the admin): mirror what publish does, verified on 1.4.0. Insert a `revisions` row (`id` ULID, `collection`, `entry_id`, `data` = JSON of the entry's fields, `author_id` null), then in one guarded `UPDATE` on `ec_<collection>` set the field columns, `live_revision_id` to the new revision, `draft_revision_id = NULL`, `updated_at`, and `version = version + 1`, `WHERE id = … AND version = <read value> AND live_revision_id = <read value>`. The search index (`_emdash_fts_<collection>`) and media-usage counters update through triggers. Verify the row, the live revision and the FTS entry afterwards; the old revision stays in history. Never null the revision pointers to "simplify" it.
- **Demo content ages.** Logic evaluated against today's date (staleness windows, upcoming events) slowly empties a seeded demo. Either seed dates relative to the deploy date, or pin the demo to a fixed moment (an `?at=` query parameter read by the page clock and carried through internal links) and give stakeholders the pinned link.

If initialisation stalls, inspect migration status and locks. Never routinely delete a lock or reset the database. On one build, an unchanged stale lock and migration records were verified before a conditional update released only that exact lock; the runtime then completed migrations. Reuse that diagnostic principle, not the project's IDs or timestamps.

Verify the production public origin before passkey registration. Behind a reverse proxy, use the installed version's supported public-origin configuration (such as `siteUrl`) and allowed-host settings where necessary. Local development access does not authenticate production. The production account should be created by its owner; record the login method, not a password or passkey secret. Confirm setup is complete and signed-out admin access reaches the intended login screen.

## Verification and handoff

Verify against running local and deployed routes rather than static `dist/` HTML alone:

- Correct list/detail pages, links and missing-entry 404 responses. `Astro.rewrite("/404")` drops the query string; pass `` `/404${Astro.url.search}` `` when the page depends on query values (a pinned demo clock, for instance).
- Imported relationships and all required composite pairs; explicit field mapping and ordering.
- Rich text, image URLs and editor-appropriate media behaviour.
- Publication visibility and preview/locale behaviour that the project actually supports.
- Applicable accessibility, design fidelity, metadata and indexing/privacy requirements. `noindex` is not access control.
- Representative server timings and query counts, plus absence of diagnosed runtime-limit errors.
- Admin setup state and sign-in behaviour; test an authorised edit/publish flow when an authenticated session is available.

**Testing the admin locally (agents).** `astro dev` only (`import.meta.env.DEV`): `GET /_emdash/api/setup/dev-bypass?content=0&redirect=/_emdash/admin` completes setup and signs in a local `dev@emdash.local` admin without a passkey (`?content=0` skips re-applying sample content); `/_emdash/api/auth/dev-bypass?redirect=/_emdash/admin` signs in when setup is already complete. Both return 403 in a built Worker. Use them to walk the editor flow (edit → draft stays private → publish → next request shows it) and record the admin labels for the handoff script. Cookies on `localhost` are shared across ports, so the dev session also shows the editor toolbar on a `wrangler dev` preview of the build; that is local only. Reset any demo edits afterwards.

Record site/admin URLs, login method, deployed version, storage resources and redeploy procedure in the project record. State any unfinished signed-in editorial verification or demo-media limitations. Do not report HTTP 200 or a successful build as proof that the full editorial workflow and performance are verified.
